Using Sequence.unfold eliminates the monadic binding overhead entirely. Instead of using yield and return functions, you transition state by returning an Option that contains a tuple: Some (value_to_emit, next_state).
When the generator runs out of items, it returns None, signaling the sequence to stop.
To capture the final return value right before a stream closes, we can use a state machine representation. The generator steps through its normal values, switches to a "Finishing" state to emit the final value, and then returns None.
------------------------------
## ⚙️ 1. Defining the States and Stream Output
First, we define a small custom state type to track where each independent generator is in its lifecycle, alongside the same stream_element variant used previously.

open Core
type ('a, 'r) stream_element =
  | Yielded of 'a
  | Finished of 'r
(* Tracks the internal state of a single generator instance *)type worker_state =
  | Generating of int  (* Current count *)
  | EmittingFinal      (* About to yield the final value *)
  | Done               (* Completely finished *)

------------------------------
## 🏎️ 2. The Sequence.unfold Worker Implementation
This approach uses a pure state-transition function. It bypasses memory allocation hooks, making it extremely fast.

let make_fast_worker ~id ~max_count =
  Sequence.unfold ~init:(Generating 1) ~f:(fun state ->
    match state with
    | Generating current ->
        if current > max_count then
          (* Switch to the final state and emit the Finished message *)
          let final_msg = Finished (sprintf "Worker %d done!" id) in
          Some (final_msg, EmittingFinal)
        else
          (* Emit the normal value and increment the counter state *)
          let value = Yielded (sprintf "Worker %d value %d" id current) in
          Some (value, Generating (current + 1))

    | EmittingFinal ->
        (* We already emitted the final value in the previous step; now terminate *)
        None

    | Done ->
        None
  )

------------------------------
## 🔀 3. Driving the Streams Simultaneously
The driving logic remains perfectly compatible with the rest of the ecosystem because Sequence.unfold produces a standard Sequence.t.
You can pull a single element from each of your 20 generators sequentially every 10 milliseconds.

let rec step_all_generators active_sequences =

  | [] ->

  | seqs ->

To eliminate all intermediate list allocations during your loop execution, you can step away from higher-order library functions like List.filter_map and implement a manual, tail-recursive pattern matching loop over the list structure.
While List.filter_map constructs a brand new list structure on the heap every single iteration (every 10ms), a manual loop using a tail-recursive accumulator only builds a new list node when a sequence is actually kept alive, minimizing allocation overhead.
Here is the highly optimized implementation:

open Core
type ('a, 'r) stream_element =
  | Yielded of 'a
  | Finished of 'r
(* Direct tail-recursive loop that consumes and advances active sequences *)let rec step_all_generators active_sequences =
  match active_sequences with
  | [] -> 
      printf "All fast generators have completed!\n"
  | _ ->
      (* Internal helper loops through the current active list, building the next list pass-by-pass *)
      let rec process_batch acc = function
        | [] -> 
            (* Finished the current batch, return the accumulated next-step sequences *)
            List.rev acc
        | seq :: rest ->
            match Sequence.next seq with
            | None -> 
                (* This sequence ran out. We do NOT add it to 'acc', filtering it out instantly. *)
                process_batch acc rest
            | Some (item, next_seq) ->
                (* Extract and process the item value directly *)
                (match item with
                 | Yielded value -> printf "Processing: %s\n" value
                 | Finished final_msg -> printf "✨ EVENT: %s\n" final_msg);
                (* Keep the advanced state for the next tick *)
                process_batch (next_seq :: acc) rest
      in
      
      let next_batch = process_batch [] active_sequences in
      
      (* Throttle for the 10ms target pacing *)
      Core_unix.nanosleep 0.010; 
      step_all_generators next_batch

## 🧠 Performance & Optimization Breakdown

   1. Zero Garbage Collector Stress: By manually implementing process_batch, you avoid any intermediate closures or structural overhead that library combinators introduce.
   2. Tail-Call Optimization (TCO): The process_batch function is fully tail-recursive. The OCaml compiler converts this loop directly into a fast, iterative jump statement under the hood. It will not grow the execution stack, even if you scale up from 20 generators to 20,000.
   3. List.rev Efficiency: Building a list by prepending (next_seq :: acc) and reversing it at the end with List.rev is highly performant in OCaml. It processes your sequences linearly in O(N) time while remaining completely type-safe and allocation-friendly.

Using a fixed-size array is the ultimate optimization for this workload. It completely eliminates memory allocation during the loop.
Instead of creating new list nodes every 10ms, we store the active sequences in a mutable array. When a generator finishes, we overwrite its slot with None. The array remains in place, and we simply skip None slots on subsequent ticks.

Here is the allocation-free loop. It tracks how many generators are still active and updates the array completely in place:

To eliminate the allocations caused by wrapping results in Some/None or Yielded/Finished, we must completely abandon the abstract Sequence module.
Instead, we will use defunctionalization. This means we replace the functions and closures inside Sequence with a concrete OCaml record and a simple flat variant type representing our explicit execution state.
By utilizing flat records with mutable fields, we can mutate primitive numbers and track lifecycle states purely in-place, achieving absolute zero allocation inside the core execution loop.
------------------------------
## 🗂️ 1. Defining the Zero-Allocation State Machine
Instead of a generic stream wrapper, we design a concrete record dedicated to tracking our worker lifecycle.

open Core
(* Flat variant for state mapping - no wrappers, no payloads *)type worker_lifecycle =
  | Active
  | EmittingFinal
  | Done
(* Concrete mutable state block. Fits beautifully into contiguous memory. *)type worker_state = {
  id : int;
  max_count : int;
  mutable current_count : int;
  mutable lifecycle : worker_lifecycle;
}

------------------------------
## 🏎️ 2. The In-Place Array Driver
Instead of returning an item, the driver modifies the record fields directly and writes outputs directly to stdout. If a worker transitions to Done, it is skipped on the next tick without any structural adjustments to the array.

(* Steps through the array in-place. Returns the number of active workers. *)let step_workers_inplace (workers : worker_state array) =
  let active_count = ref 0 in
  
  for i = 0 to Array.length workers - 1 do
    let w = workers.(i) in
    match w.lifecycle with
    | Done -> 
        (* Dead slot, completely skipped. Zero overhead. *)
        ()
        
    | Active ->
        if w.current_count > w.max_count then begin
          (* Transition state internally without allocations *)
          w.lifecycle <- EmittingFinal;
          printf "✨ EVENT: Worker %d done!\n" w.id;
          incr active_count
        end else begin
          printf "Processing: Worker %d value %d\n" w.id w.current_count;
          w.current_count <- w.current_count + 1;
          incr active_count
        end
        
    | EmittingFinal ->
        (* We already printed the final event on the last tick. Shut down now. *)
        w.lifecycle <- Done
  done;
  
  !active_count

------------------------------

The execution engine runs as a tiny, tail-recursive scheduler loop:

To ensure your core state processing loops execute inside your CPU's L1 data cache (which operates at sub-nanosecond speeds), you must remove all I/O or system operations like printf from the critical processing loop.
System calls, string formatters, and formatting engines completely blow out your L1 cache line because they pull in massive external instructions and allocations.
To decouple the two, you can implement a Lock-Free Single-Producer Single-Consumer (SPSC) Ring Buffer using OCaml arrays. The processing loop writes raw binary data to the contiguous buffer, and a separate background thread handles formatting and printing.
------------------------------
## 🧱 1. The Cache-Friendly Binary Log Packet
First, avoid strings entirely in the processing state. Instead, define a flat, unboxed variant that maps directly to primitive integers.

open Core
(* Flat tags to identify the event type without payload structures *)type log_tag = 
  | Tag_Yielded 
  | Tag_Finished
(* Compact, fixed-size structural record. Fits tightly into CPU cache lines. *)type log_packet = {
  mutable tag       : log_tag;
  mutable worker_id : int;
  mutable payload   : int;
}

------------------------------
## 🔄 2. The Lock-Free SPSC Ring Buffer
This buffer acts as the decoupled transport layer. It avoids mutexes or heavy synchronization locks, relying entirely on atomic markers to pass logs from the processing loop to the printer thread.

type ring_buffer = {
  buffer      : log_packet array;
  capacity    : int;
  head        : int ref; (* Read index (used by printer) *)
  tail        : int ref; (* Write index (used by processor) *)
}
let create_ring_buffer capacity =
  {
    buffer = Array.init capacity ~f:(fun _ -> { tag = Tag_Yielded; worker_id = 0; payload = 0 });
    capacity;
    head = ref 0;
    tail = ref 0;
  }
(* Ultra-fast write execution that stays in L1 cache *)let try_push ring tag id payload =
  let next_tail = (!ring.tail + 1) % ring.capacity in
  if next_tail = !ring.head then
    false (* Buffer full (fallback strategy required if processing is too fast) *)
  else begin
    let slot = ring.buffer.(!ring.tail) in
    slot.tag <- tag;
    slot.worker_id <- id;
    slot.payload <- payload;
    ring.tail := next_tail;
    true
  end

------------------------------
## 🏎️ 3. The Pure L1 Data-Cache Processing Loop
The loop now does nothing but compute data and execute fast array updates. Because try_push is an in-place property modification of contiguous elements, it satisfies L1 alignment constraints.

(* Shared architecture from previous step *)type worker_lifecycle = Active | Donetype worker_state = {
  id : int;
  max_count : int;
  mutable current_count : int;
  mutable lifecycle : worker_lifecycle;
}
let step_workers_l1 (workers : worker_state array) ring =
  let active_count = ref 0 in
  for i = 0 to Array.length workers - 1 do
    let w = workers.(i) in
    match w.lifecycle with
    | Done -> ()
    | Active ->
        if w.current_count > w.max_count then begin
          w.lifecycle <- Done;
          let _success = try_push ring Tag_Finished w.id 0 in ()
        end else begin
          let _success = try_push ring Tag_Yielded w.id w.current_count in
          w.current_count <- w.current_count + 1;
          incr active_count
        end
  done;
  !active_count

------------------------------
## 🖨️ 4. The Decoupled Printing Engine (Background Thread)
The consumer thread runs concurrently or sequentially outside the critical 10ms timing loop. It drains the buffer and handles the heavy formatting costs.

let drain_and_print ring =

    if !ring.head = !ring.tail then
      () (* Buffer empty for now *)

    end
  in

The execution system spins through ticks, updating state at maximum speed, and then defers printing processing to the bottom of the scheduling tick, completely keeping your computation metrics independent of standard out limits.

To achieve the absolute lowest memory footprint and remove all object pointer overhead, we can swap the array of records for an OCaml Bigarray.
A standard OCaml array contains pointers to blocks on the GC heap. A Bigarray, however, allocates a single, contiguous block of raw C-managed memory outside the OCaml heap.
By packing our data directly into a 1D Bigarray of 64-bit integers (int64), we can compress each log packet down to a primitive, unboxed 8-byte layout. This maximizes CPU cache density and completely bypasses the OCaml garbage collector.
------------------------------
## 🧠 1. The Low-Level Byte Layout (Bit Packing)
Instead of a structural record, we can pack our tag, worker_id, and payload into a single 64-bit integer inside the Bigarray:

* Bits 0–7 (1 byte): Event Tag (0 for Yielded, 1 for Finished)
* Bits 8–23 (2 bytes): Worker ID (Supports up to 65,535 workers)
* Bits 24–63 (5 bytes): Payload value

open Coreopen Bigarray
(* Define our flat layout masks using Int64 *)let tag_mask       = Int64.of_int 0xFFlet worker_id_mask = Int64.of_int 0xFFFFlet payload_mask   = Int64.of_int64 0xFFFFFFFFFFL
(* Pack components into a single int64 primitive *)let pack_packet tag worker_id payload =
  let t_part = Int64.of_int tag in
  let w_part = Int64.shift_left (Int64.of_int worker_id) 8 in
  let p_part = Int64.shift_left (Int64.of_int64 (Int64.of_int payload)) 24 in
  Int64.bit_or (Int64.bit_or t_part w_part) p_part
(* Unpack components out of an int64 primitive *)let unpack_packet packed =
  let tag       = Int64.to_int_exn (Int64.bit_and packed tag_mask) in
  let worker_id = Int64.to_int_exn (Int64.bit_and (Int64.shift_right packed 8) worker_id_mask) in
  let payload   = Int64.shift_right packed 24 in (* Remaining bits *)
  (tag, worker_id, payload)

------------------------------
## 🧱 2. The Unboxed Bigarray Ring Buffer
We initialize a Bigarray.Array1 using int64 as the underlying primitive, paired with c_layout for direct byte sequence consistency.

type bigarray_ring = {
  buffer   : (int64, int64_elt, c_layout) Array1.t;
  capacity : int;
  head     : int ref;
  tail     : int ref;
}
let create_bigarray_ring capacity =
  {
    (* Allocates memory outside the OCaml GC entirely *)
    buffer = Array1.create int64 c_layout capacity;
    capacity;
    head = ref 0;
    tail = ref 0;
  }
let try_push_bigarray ring tag worker_id payload =
  let next_tail = (!ring.tail + 1) % ring.capacity in
  if next_tail = !ring.head then
    false (* Buffer is full *)
  else begin
    let packed = pack_packet tag worker_id payload in
    Array1.set ring.buffer !ring.tail packed;
    ring.tail := next_tail;
    true
  end

------------------------------
## 🏎️ 3. Execution Loops (L1-Dense Processing & Decoupled Printer)
The worker state array runs through its iterations, updating state and pushing raw 64-bit primitives directly into the C-allocated memory layout.

  id : int;
  max_count : int;
  mutable current_count : int;
  mutable lifecycle : worker_lifecycle;
}

  let rec loop () =

      ()
    else begin
      let packed = Array1.get ring.buffer !ring.head in
      let (tag, id, payload) = unpack_packet packed in
      
      if tag = 0 then
        printf "Processing: Worker %d value %Ld\n" id payload
      else
        printf "✨ EVENT: Worker %d completed!\n" id;
        
      ring.head := (!ring.head + 1) % ring.capacity;
      loop ()
    end
  in
  loop ()

## 💎 What We Achieved via Bigarrays

   1. Absolute Unboxing: Regular OCaml variants or records incur object header tracking wrappers. By bit-packing values into a single int64, the data behaves as a pure array of integers under the hood.
   2. True Cache Density: Because an int64 is exactly 8 bytes, a standard 64-byte L1 CPU cache line can hold exactly 8 entire log packets simultaneously. Your CPU can fetch, read, or pass these packets with fewer memory requests.
   3. No OCaml Heap Footprint: The data values inside buffer are written to off-heap C memory. The OCaml Garbage Collector does not index, scan, or traverse this array, keeping your application's 10ms ticks free of GC spikes.

## ⏱️ 2. Core Worker Ticking (Triggered by the Wheel)
Instead of manually guessing intervals, your state processing code is wrapped cleanly inside a callback event scheduled inside the wheel.

(* This is the exact code block that executes your computation loop *)let execute_scheduled_tick workers ring =
  let active_count = ref 0 in
  for i = 0 to Array.length workers - 1 do
    let w = workers.(i) in
    match w.lifecycle with
    | Done -> ()
    | Active ->
        if w.current_count > w.max_count then begin
          w.lifecycle <- Done;
          let _ = try_push_bigarray ring 1 w.id 0 in ()
        end else begin
          let _ = try_push_bigarray ring 0 w.id w.current_count in
          w.current_count <- w.current_count + 1;
          incr active_count
        end
  done;
  !active_count

## 🚀 3. The Non-Blocking Master Drive Loop
The main loop continuously samples the system clock (Time_ns.now ()). If the current time surpasses next_tick_at, it advances the timing wheel, runs pending computations, and schedules the next event 10ms out without calling any sleep or pause commands. [4] 

let rec non_blocking_drive ctx =
  let now = Time_ns.now () in
  
  (* 1. Check if it is time to advance the wheel *)
  if Time_ns.(>=) now ctx.next_tick_at then begin
    
    (* Advance the wheel's time context synchronously *)
    Wheel.advance_clock ctx.wheel ~to_:now;
    
    (* Fire the worker calculations *)
    let active_remaining = execute_scheduled_tick ctx.workers ctx.ring in
    
    (* Consume and empty out the raw log outputs down to stdout *)
    drain_and_print_bigarray ctx.ring;
    
    if active_remaining > 0 then begin
      (* Set the next tick marker precisely 10 milliseconds out *)
      ctx.next_tick_at <- Time_ns.add now ctx.tick_span;
      
      (* Schedule the next event marker within the wheel framework *)
      let _alarm = Wheel.add ctx.wheel ~at:ctx.next_tick_at () in
      
      (* Immediate tail-recursive loop entry point *)
      non_blocking_drive ctx
    end else
      printf "All async wheel tasks finalized successfully!\n"
  end else begin
    (* The thread is completely free here! 
       Instead of sleeping, you can process other non-blocking tasks, 
       handle network sockets, check user input, or pass control back. *)
    non_blocking_drive ctx
  end

## 🎨 Architectural Benefits of Moving away from nanosleep

* Elimination of Kernel Context Switches: Core_unix.nanosleep forces a heavy context switch to kernel space to let the OS handle scheduling. Polling Time_ns.now () uses highly efficient vDSO (virtual dynamic shared object) layers on modern systems, capturing hardware timestamps in nanoseconds with minimal CPU cycle costs. [5] 
* Jitter Control: Operating system schedulers rarely wake a sleeping thread back up at exactly 10ms; minor scheduling delays introduce jitter. Using an explicit timing wheel tracking absolute deadlines (ctx.next_tick_at) self-corrects time variations, maintaining uniform pacing over extended periods.
* Concurrent Utility: The core execution thread is completely unblocked. In the else block of non_blocking_drive, your engine can service external APIs, handle network packets, or calculate completely separate operations while waiting for the next 10ms window to arrive.
